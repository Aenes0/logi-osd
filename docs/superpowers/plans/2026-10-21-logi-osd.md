# logi-osd — Plano de Implementação

> **Para agentes:** SUB-SKILL OBRIGATÓRIA: use `superpowers:subagent-driven-development` (recomendado) ou `superpowers:executing-plans` para executar este plano tarefa a tarefa. Os passos usam checkbox (`- [ ]`).

**Objetivo:** daemon de sessão em Rust que mostra uma pílula de aviso no centro inferior da tela para eventos de dispositivos Logitech (lock keys, Fn, luz do teclado, bateria, carga, conexão, tecla Emoji), lendo HID++ por hidraw, sem polling e sem toolkit gráfico.

**Arquitetura:** uma thread por nó hidraw HID++ (receptor Bolt/Unifying/Nano/Lightspeed, ou dispositivo Bluetooth direto) dorme em `poll()` e traduz frames em `NodeEvent`s, enviados por `calloop::channel` à thread principal. A thread principal roda um `calloop::EventLoop` com Wayland (layer-shell via sctk), monitor udev (hotplug de `hidraw`), o canal dos nós e um único timer de esconder a pílula. Toda a lógica (frames, casamento de request, decodificação, bateria, regras, textos, layout, tema, config) é pura e testada com fixtures capturados na sonda de hardware (Tarefa 1).

**Tech stack:** Rust 1.99, edition 2024; `smithay-client-toolkit 0.20.0` (`default-features = false`, `features = ["calloop"]`; usar `sctk::reexports::{calloop, calloop_wayland_source, client}`), `tiny-skia 0.11.4` (`default-features = false`, `features = ["std", "simd"]`), `ab_glyph 0.2.32`, `udev 0.9.3`, `rustix 1` (`features = ["event", "fs"]`), `libc 0.2`. Nada de tokio, tracing, serde, libcosmic. Todos já estão em `~/.cargo/registry`.

**Spec:** `docs/superpowers/specs/2026-10-21-logi-osd-design.md` (fonte da verdade). Mockup: `~/.cache/keyboard-osd-brainstorm/.superpowers/brainstorm/*/content/luz-teclado-v2.html` (opção 3 + fileira "outros avisos", estilo B).

### Tarefa 1: [opus] Sonda de hardware — protocolo real, interpretação

Sonda descartável em Python (stdlib apenas: `os`, `select`, `struct`, `time`, `sys`, `pathlib`), rodando no host. Não usa a biblioteca do Solaar (evita depender da versão), mas reproduz o framing dela. Saída: fixtures hex + `resultados.txt` com respostas `chave = valor`. **Esta tarefa termina num portão: o controller apresenta `resultados.txt` ao usuário e só segue para as tarefas que dependem dos ramos depois de aprovação.**

**Files:**
- Create: `tools/probe/hidpp_probe.py`
- Create (gerados pela execução): `tests/fixtures/probe/info.txt`, `tests/fixtures/probe/<cenario>.hex`, `tests/fixtures/probe/resultados.txt`

**Interfaces:**
- Produces: formato de fixture usado por todas as tarefas seguintes — uma linha por frame recebido:
  `<t_ms> <nó> <hex bytes separados por espaço>`, onde `<nó>` é o PID do receptor/dispositivo em minúsculas (estável entre boots; ex.: `  1234 c548 11 01 0a 00 02 00 ...`), linhas `# ` são comentários (o roteiro escreve `# prompt: ...`, `# feature 0x0a = 0x4220 (dev 1)`). O `.hex` inclui só frames **recebidos**, completos (7 ou 20 bytes).
- Produces: `resultados.txt` com exatamente as chaves listadas no Passo 5.

**Framing (verificado no código do Solaar 1.1.20, `base.py`/`hidpp20.py`/`receiver.py`):**
- Curto: `[0x10, dev, sub_id, address, p0, p1, p2]` (7 bytes). Longo: `[0x11, dev, sub_id, address, p0..p15]` (20 bytes). Ler com buffer de 32.
- HID++ 2.0 request: `sub_id = índice da feature`, `address = (função << 4) | 0x0C`. Evento: `address & 0x0F == 0`, evento = `address >> 4`.
- Registrador HID++ 1.0 (receptor `dev = 0xFF`): leitura curta `sub_id 0x81`, escrita curta `0x80`, leitura longa `0x83` (registrador `0x2B5` → `sub 0x83, addr 0xB5`). Erro 1.0: `[0x10, dev, 0x8F, sub_req, addr_req, err, 0]`. Erro 2.0: `[0x11, dev, 0xFF, idx_req, addr_req, err, ...]`.
- Ping/versão: `[0x10, dev, 0x00, 0x1C, 0x00, 0x00, 0xAA]` → resposta `sub 0x00, addr 0x1C, [major, minor, 0xAA]`; dispositivo 1.0 responde erro `0x8F` código `0x01`.
- ROOT `getFeature` (feature 0x0000, índice 0, fn 0): params `[id_hi, id_lo]` → `[índice, tipo, versão]` (índice 0 = ausente).
- Receptor: flags = registrador `0x00` (3 bytes; bit WIRELESS = `0x000100`, SOFTWARE_PRESENT = `0x000800`); gatilho de chegada = escrever registrador `0x02` com `[0x02, 0x00, 0x00]` → o receptor emite uma notificação `0x41` por dispositivo pareado. `0x41`: `dev` = índice, `address` = protocolo (`0x10` = Bolt), `p0 & 0x40` = link **não** estabelecido, wpid = `p2 << 8 | p1`.
- Seleção de nós (igual a `hidapi/udev_impl.py` do Solaar): vendor `046D` e descritor com report de **entrada** `0x10` de 6 bytes **ou** `0x11` de 19 bytes (sem exigir usage page: no Bluetooth a página é `0xFF43`, não `0xFF00`); ignorar nó USB com driver `logitech-hidpp-device` (filho DJ). Os números `hidrawN` mudam a cada boot: sempre usar a saída de `listar`. No boot de hoje: `hidraw7` = Bolt `C548`, `hidraw3` = Nano `C537`, `hidraw4` = filho DJ do G602.
- Notificação nula: `sub_id == 0x00` com `address & 0x0F == 0` é no-op (Solaar `base.py` `make_notification`) — a sonda anota, mas não conta como evento.
- K375S FN INVERSION (0x40A3), como `settings_templates.py` do Solaar (`find_current_host`): prefixo = byte 3 da resposta de HOSTS_INFO (0x1815) fn0; leitura = fn0 com params `[prefixo]`; estado = byte 1 da resposta (pula 1 byte).
- Ligar/acordar: notificação HID++ 1.0 `sub_id 0x4B` com `address 0x01` = "powered on" (Solaar `common.py` `Notification.POWER`, `notifications.py`).
